The map of a Rust process

Inside those virtual pages, your program's memory is split into neighbourhoods. Each one has a different job and different rules.

Each region in plain words

  1. Text (code). Your fn main turned into machine instructions. Read + execute, never write. That's a safety feature: a bug can't overwrite your code.
  2. Data. Things known when you compile: static values and string literals. Read-only data (like "hello") technically lives in a sub-part called .rodata (read-only data).
  3. BSS ("Block Started by Symbol", an old name). Statics that start as zero. The file doesn't need to store all those zeros, the OS just hands over zeroed pages at start-up. In Rust every static must have a value, so BSS = "statics that start at 0".
  4. Heap. Memory you ask for while the program runs. Grows upward.
  5. Stack. Function calls. Grows downward. Each thread gets its own stack.
  6. Environment. The very top holds argv (command-line args) and environment variables like PATH.

Analogy: a building. The ground floor (code) is locked glass: you can look, you can't change it. The stack is like stacking boxes down from the ceiling, the heap is stacking boxes up from the floor, and they share the empty middle.

Two honest footnotes

ASLR. The OS shifts every region by a random amount each time you run (Address Space Layout Randomisation). That makes attacks harder. So the exact addresses change between runs, but the order of regions stays the same.

The order of the bottom parts depends on the system. On macOS the code comes first, then read-only data, as drawn. On Linux, read-only data (like string literals) is usually placed below the code. On both, everything read-only sits below the writable statics, and the heap and stack come after. memscope's tests caught this difference.

It's a simplified picture. Real systems also map big heap allocations and shared libraries in other places. The map above is the right mental model for this course.
