Virtual memory and pages

Your program never sees real RAM. It sees a pretend, private copy of memory, and the operating system quietly translates.

In one sentenceEvery program gets its own fake address space, cut into pages, and the OS + CPU map each page to a real spot in RAM.

The problem

Your computer runs hundreds of programs at once, but there is only one RAM. If every program used real RAM addresses directly:

  • Two programs could write to the same spot and break each other.
  • Every programmer would need to know which bits of RAM are free right now.
  • A buggy program could read your browser's passwords.

The fix: virtual memory

  1. Each program (a process) gets its own huge range of addresses, starting at 0. These are virtual addresses. They're not real.
  2. That range is cut into equal blocks called pages. Usually 4 KB each. (On Apple Silicon Macs they're 16 KB.)
  3. The operating system kernel keeps a page table for each process: "this program's page 1 is really at RAM frame 3".
  4. A piece of hardware inside the CPU, the MMU (Memory Management Unit), reads that table and translates every single address, super fast.

Analogy: your program has a notebook with page numbers 0, 1, 2, 3... The OS is a librarian with a list saying "notebook page 1 is really stored on shelf 3, page 2 on shelf 98". You just say "page 2", and the librarian fetches it. You never need to know about shelves.

Virtual (what your program sees):  [Page 0] [Page 1] [Page 2] [Page 3]
                                       |        |        |        |   MMU translates
                                       v        v        v        v
Physical (real RAM):               frame 12  frame 3  frame 98  frame 25

Notice: the pages look side by side to your program, but they're scattered in real RAM. That's fine. Your program never knows.

Permissions: every page has rules

Each page in the table also has three switches:

FlagMeansExample
R readYou may look at itAlmost everything
W writeYou may change itStack, heap. Not your code.
X executeThe CPU may run it as instructionsOnly your compiled code

Break a rule (write to a read-only page, or touch a page you were never given) and the CPU stops your program. On Mac/Linux this is the famous segmentation fault ("segfault").

What's a page fault?

When your program touches a page, one of three things happens:

  1. Page is in RAM. Normal. Fast. Nothing to see.
  2. Page is yours but was moved to disk (RAM was full). The MMU raises a page fault, the OS loads it back from the SSD, and your program continues. It never notices, it's just slower.
  3. Page isn't yours, or the permission is wrong. The OS kills the program: segfault.

Case 2 is how a program can use more memory than you have RAM. Case 3 matters a lot in Lesson 2: some memory bugs crash (case 3) and some don't (the bad address happened to be on a page you own).

Try it (no install needed)

Open the Terminal on your Mac and type:

pagesize

On an M-series Mac you'll see 16384 (16 KB). On most Linux/Intel machines it's 4096 (4 KB).

Check yourself

Two programs both use address 0x1000. Do they clash?No. Each has its own virtual address space, so their 0x1000 maps to different real RAM.
Who translates virtual addresses into physical ones?The MMU (hardware in the CPU), using the page table that the kernel (the OS) sets up.
If I just make up an address like 0x123456 in my program and read it, will it work?Only if that address is inside a page the OS gave to your process with read permission. Usually it isn't, so you'd get a segfault. Having a number is not the same as having permission.
Can a stack overflow happen even if the computer has lots of free RAM?Yes. The stack has its own small size limit (a few MB) that is separate from how much RAM is free. You'll see it happen in Part 1.6.
