The stack and stack frames

The stack is how your program remembers which function it's in and what each function's variables are.

In one sentenceEvery function call pushes one frame onto the stack, and returning pops it off, so the newest call is always finished first.

A stack of plates

Each time a function is called, put a plate on the pile. You can only take the top plate off. When a function finishes, its plate is removed and you're back at the plate underneath.

Each plate is a stack frame (also called a call frame). It holds:

  • the arguments passed into the function
  • the function's local variables
  • space for the return value (and where to jump back to)

In memory the stack grows downward, so the newest frame is drawn at the bottom.

Why the stack is fast

  1. The compiler knows the exact size of every frame before the program runs (main needs 2 × 4 bytes for two i32s).
  2. So "allocating" a frame is just moving one CPU register (the stack pointer) down by that many bytes. "Freeing" moves it back up. That's it.
  3. Recently used stack memory is almost always in the CPU cache, so reading it is very quick.

The rules of the stack

Good atBad at
Super fast allocate and freeSmall: usually 8 MB for the main thread, 2 MB for threads Rust spawns
Automatic cleanup when the function endsData dies when the function ends: you can't return a reference to a local
Each thread has its own stack, so no sharing problemsOnly for data whose size is known at compile time
Cache friendlyBig arrays can cause a stack overflow
"Size known at compile time" means the compiler can count the bytes just by reading the type. i32 = 4. [u8; 5] = 5. But [i32] (a slice of some length) or str (text of some length) have no fixed size, so they can't sit directly on the stack. They need a pointer, which is Part 1.4.

Check yourself

In the example, is input the same memory as x?No. input is a copy of x placed in foo's own frame. Changing input would not change x.
After foo returns, what happens to y?It's gone. foo's whole frame was popped. Only the return value (21) made it back into main's result.
Why can't you return &y from foo?Because y lives in foo's frame, which is destroyed when foo returns. The reference would point at dead memory. Rust refuses to compile it.
Two i32 locals in the same frame: how far apart are their addresses, usually?4 bytes, because each i32 is 4 bytes. (The compiler may reorder them, so don't rely on which comes first.)
