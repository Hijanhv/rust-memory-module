What a memory bug really is

Before we write broken code on purpose, let's define exactly what "broken" means.

In one sentenceA memory bug is touching memory you're not allowed to touch right now, and the result is undefined behaviour: anything can happen.

The formal definition of memory safety

A program is memory safe if every time it reads or writes memory, all of these are true:

  1. The memory is allocated (it belongs to a real, existing value).
  2. The access is inside the bounds of that value (not past its end).
  3. The value is still alive (not freed yet).
  4. If other threads use it too, the access is synchronised (a lock or an atomic).

Break any one and you have a memory bug. They group into three families:

FamilyQuestion it asksBug in this lesson
Spatial safetyWhere: is this address inside the object?Buffer overflow
Temporal safetyWhen: is the object still alive?Use-after-free
Thread safetyWho: is anyone else touching it at the same time?Data race

Analogy: a hotel room. Spatial bug = walking into the room next to yours. Temporal bug = using your key after you checked out (someone else may be staying there now). Data race = two guests booked into the same room, both rearranging the furniture.

Undefined behaviour (UB)

This is the most important idea in the lesson.

  1. The compiler is allowed to assume your program never does UB. It optimises your code based on that promise.
  2. So when UB happens, the rules are off. Not "you get a random number". Literally no guarantee about anything, including code far away from the bug.
  3. It might crash. It might print garbage. It might look perfectly fine on your laptop and fail on a server. The last one is the scariest.
"It worked when I ran it" proves nothing when UB is involved. A program with UB is broken even on the runs where the output looks right.

Safe Rust vs unsafe Rust

In safe Rust (normal Rust), the compiler proves all four rules above for you. If it can't prove it, it won't compile. That's why safe Rust can't have these bugs at all.

Inside an unsafe { } block you get five extra powers. The compiler trusts you to follow the rules:

  1. Follow (dereference) a raw pointer (*const T, *mut T)
  2. Call an unsafe fn
  3. Read or write a static mut
  4. Implement an unsafe trait
  5. Read fields of a union

That's all. unsafe does not switch off the borrow checker or type checks. It only unlocks those five things. The next three lessons use powers 1 and 3.

Why unsafe exists at all: talking to hardware, calling C libraries, and building things like Vec itself. Vec is written with unsafe code inside, carefully, so that you get a safe interface.

Check yourself

Reading index 10 of a 5-item array: spatial or temporal?Spatial. It's about where: outside the bounds.
Reading a Box after it was dropped: spatial or temporal?Temporal. The address may be fine, but the value is no longer alive.
My UB program printed the right answer 100 times. Is it OK?No. UB means the compiler and hardware owe you nothing. A different compiler version, optimisation level or machine can change the result.
Does unsafe turn off the borrow checker?No. It only unlocks five specific powers, like dereferencing raw pointers and touching static mut.
