See it on your own machine

Diagrams are nice. Real addresses are better. Let's print where things actually live.

In one sentencePrinting addresses with {:p} proves the map from Part 1.2 is real: code and statics low, heap above them, stack way up high.

Set up (one time)

  1. Clone the repo: git clone https://github.com/Hijanhv/rust-memory-module
  2. Go into the lab folder: cd rust-memory-module/lab
  3. Run any example: cargo run --example 01_addresses

No internet? No Rust installed? Paste any example file into the free Rust Playground and press Run.

Example 1: one address from every region

cargo run --example 01_addresses

My output (yours will have different numbers because of ASLR, but the same order):

text  (code)    main()   : 0x100590ce8
static (ro)     GLOBAL   : 0x1005c77bc
static (ro)     "hello"  : 0x1005c77b4
static (rw)     COUNTER  : 0x1005dccc8
heap            *on_heap : 0x100e453b0
stack           on_stack : 0x16f86e724
stack           on_heap  : 0x16f86e728  (the Box itself, i.e. the pointer)

Read it bottom-up like the map:

  1. Code is lowest (0x100590...).
  2. Read-only statics just above it, then the writable static COUNTER a bit higher.
  3. Heap above that (0x100e...).
  4. Stack far away at 0x16f... with a huge gap in between, just like the picture.
  5. The Box variable on_heap is on the stack, but the 99 inside it is on the heap. Two different addresses for one variable.

Example 2: how big is each thing on the stack?

cargo run --example 05_sizes
i32               4 bytes
[i32; 5]         20 bytes (whole array is on the stack)
&i32              8 bytes (thin pointer: address only)
Box<i32>          8 bytes (thin pointer to heap)
&str             16 bytes (fat: address + length)
&[i32]           16 bytes (fat: address + length)
String           24 bytes (ptr + len + capacity)
Vec<i32>         24 bytes (ptr + len + capacity)
Box<dyn Speak>   16 bytes (fat: address + vtable)
Option<Box<i32>>  8 bytes (null is never a valid Box, so None is free)

A thin pointer is just an address (8 bytes on 64-bit). A fat pointer is an address plus extra info: a length for slices and &str, or a table of methods (vtable) for dyn traits. This is how unsized things like str and [i32] can be used: through a fat pointer that carries the size.

Example 3: a real stack overflow

cargo run --example 06_stack_overflow
heap version worked: 4194304 bytes

thread '<unknown>' has overflowed its stack
fatal runtime error: stack overflow, aborting

A thread Rust spawns gets a 2 MB stack. We tried to put a 4 MB array on it. Boom. The same 4 MB in a vec! (heap) was totally fine. That's the stack size limit from Part 1.3, and it happened while the computer had gigabytes of free RAM.

Check yourself

Why is &str 16 bytes but &i32 only 8?&str is a fat pointer: 8 bytes of address + 8 bytes of length. &i32 only needs the address because an i32 is always 4 bytes.
Why are String and Vec both 24 bytes?Both store pointer + length + capacity, 8 bytes each. (A String is a Vec of bytes underneath.)
A 4 MB array crashed but a 4 MB Vec didn't. Why?The array lives on the 2 MB thread stack. The Vec's data lives on the heap, and only 24 bytes go on the stack.
