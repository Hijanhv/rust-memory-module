Static memory and strings

Some data is baked into your program file and exists from the first instruction to the last.

In one sentenceStatic memory is fixed when you compile, lives for the whole program, and is never freed.

What lives in static memory

  1. String literals. Any text in double quotes, like "Hello". Always static, automatically. You don't write static.
  2. Static variables you declare with static NAME: Type = value;.

Analogy: static memory is text printed in a book. It's there before you open it and still there when you close it. The stack and heap are sticky notes you add and remove while reading.

Scope vs lifetime (the tricky bit)

These two words sound similar but mean different things:

  • Lifetime = how long the memory exists. For statics: the whole program.
  • Scope = where in your code the name can be used.

A static declared inside a function has a short scope (only that function can say its name) but a full-program lifetime (the memory never goes away).

Rules for statics

The value must be known at compile time. So these fail:

fn main() {
    static NUMBERS: Vec<i32> = vec![5, 6];   // ERROR: vec! allocates on the heap at runtime
    let n: i32 = 55;
    static NUMBER: i32 = n;                  // ERROR: n is a runtime stack value
}

And changing a static needs static mut plus unsafe, because any thread could touch it at any time. That's exactly the data race in Lecture 2.

static vs const. A const is copied into every place you use it (no single address). A static has exactly one fixed address in memory. Use const for plain constants, static when you need one shared location.

Try it 
cargo run --example 04_static_strings

Two identical literals print the same address (stored once). The String copy prints a different, heap address.

Inspect the binary yourself

The lecture mentions looking inside the compiled program file to find where statics went. Your Mac already has the tools for this. Build the lab first (cd lab && cargo build --examples), then:

size -m target/debug/examples/04_static_strings

This lists the sections of the file. The important ones on my Mac:

Section __text:    219156        <- your compiled code (text segment)
Section __cstring:   6227        <- string literals
Section __const:     7192        <- read-only statics
Section __data:      2496        <- writable statics with a value
Section __bss:        136 (zerofill)  <- statics that start at zero (no bytes stored!)

Notice __bss says zerofill: the file doesn't store those zeros at all, the OS creates zeroed pages at start-up. That's the BSS idea from Part 1.2. Now find our two statics by name:

nm -m target/debug/examples/04_static_strings | grep GREETING
00000001000480c0 (__DATA_CONST,__const) non-external __ZN18_04_static_strings14GREETING_OUTER17h261fd703d6e66ddeE
00000001000480d0 (__DATA_CONST,__const) non-external __ZN18_04_static_strings5hello14GREETING_INNER17hb9b47180dca2aa29E
  • Both statics have a fixed address decided when the program was built, just 16 bytes apart.
  • GREETING_INNER was declared inside the function hello, and its symbol name contains 5hello. Its scope is the function, but it lives in the same static section as the global one.
  • They are 16 bytes each because a &str is a fat pointer (address + length). The letters themselves are in __cstring.
  • The odd __ZN...17h...E wrapping is name mangling: the compiler adds the module path and a hash so names never clash.

On Linux the same sections are called .text, .rodata, .data and .bss. Use size -A and nm there.

Check yourself

Is a string literal on the stack, heap, or static?Static (read-only). A &str variable on the stack just points at it.
After a function with a local static returns, is the static's memory freed?No. The memory lives for the whole program. Only the name stops being usable outside that function.
What does String::from("hi") do in memory?Allocates a heap block and copies the bytes of the static literal "hi" into it. Now there are two copies: one static, one on the heap.
Why does the BSS section take almost no space in the program file?It only holds zeros, so the file just records "this many zero bytes", and the OS creates zeroed pages when the program starts.
Why can't static V: Vec<i32> = vec![1]; compile?vec! needs the heap at runtime, but a static's value must be fully known at compile time.
