Ownership, borrowing and slices

The single most important chapter in the Rust Book. Lecture 2 is basically "what happens when you break these rules".

In one sentenceEvery value has one owner, you can lend it out with references, and when the owner leaves its scope the value is cleaned up.
From the Rust Book: 4.1 What is ownership?, 4.2 References and borrowing, 4.3 Slices. The Book itself explains ownership using the stack and the heap, which is why this module teaches memory first.

The three rules

  1. Each value in Rust has an owner.
  2. There can only be one owner at a time.
  3. When the owner goes out of scope, the value is dropped.

Scope = the { } block where a variable is valid. It starts when you declare it and ends at the closing }.

{                         // s doesn't exist yet
    let s = String::from("hello");   // s is valid from here
    // use s
}                         // scope over: Rust calls drop, the heap memory is freed

Move: the house key

Why does Rust do this? If both s1 and s2 stayed valid, at the end of the scope both would try to free the same heap memory. That's a "double free", a cousin of use-after-free. Moving makes it impossible.

Copy: simple values are just duplicated

let x = 5;
let y = x;          // i32 is Copy: the 4 bytes are duplicated on the stack
println!("{x} {y}"); // both work

Types that live entirely on the stack and are cheap to duplicate are Copy: all integers, floats, bool, char, and tuples/arrays of those. Anything that owns heap memory (String, Vec, Box) is not Copy. If you really want a second heap copy, ask for it: let s2 = s1.clone();

Functions move things too

fn takes(s: String) { }          // s is dropped at the end of this function

let s = String::from("hi");
takes(s);                        // ownership moved into the function
// println!("{s}");              // ERROR: value moved

Passing a value to a function works exactly like let s2 = s1;. That would be annoying if you just wanted the function to look at it. So we have borrowing.

Borrowing: lend it, don't give it away

fn length(s: &String) -> usize {  // &String = a reference, a borrow
    s.len()
}                                 // s goes out of scope, but it doesn't own anything, so nothing is freed

let s = String::from("hi");
let n = length(&s);               // lend s
println!("{s} has {n} letters");  // s is still ours

A reference is basically an address of the value plus a promise from the compiler that the value will still be alive while you use it.

To change something you borrowed, you need a mutable reference:

fn add_bang(s: &mut String) { s.push_str("!"); }

let mut s = String::from("hi");
add_bang(&mut s);

The borrowing rules

At any moment you can have either:

  • any number of & (read-only) references, or
  • exactly one &mut (read-write) reference.

And every reference must always point at a value that's still alive.

let mut s = String::from("hi");
let r1 = &mut s;
let r2 = &mut s;        // ERROR: cannot borrow `s` as mutable more than once
println!("{r1} {r2}");

The Book says this rule exists to prevent data races at compile time. That's the exact bug in Part 2.4. Many readers or one writer, never both.

Dangling references

fn dangle() -> &String {
    let s = String::from("hi");
    &s                  // ERROR: s is dropped when dangle ends
}

A dangling reference points at memory that has been freed. In C this compiles and becomes a use-after-free. In Rust it's a compile error. (The fix: return the String itself, moving ownership out.)

Slices: a view into part of something

let s = String::from("hello world");
let hello: &str = &s[0..5];     // a slice: points into s, length 5
let world: &str = &s[6..11];

let a = [1, 2, 3, 4, 5];
let mid: &[i32] = &a[1..3];     // [2, 3]

A slice is a reference to a run of items. It stores two things: where it starts and how long it is. That's a fat pointer, 16 bytes. And a string literal like "hi" has type &str: it's a slice pointing into the program's static memory. You'll see this in Part 1.5.

Check yourself

let a = vec![1]; let b = a; Can you use a?No. The Vec moved to b. Only one owner, so only one variable will free the heap memory.
Why can you still use x after let y = x; when x is an i32?i32 is Copy. The 4 bytes are simply duplicated. No heap memory, so no double free risk.
Can you have two &mut to the same value at the same time?No. One &mut OR many &. This rule prevents data races.
What's a dangling reference?A reference to memory that has already been freed. Rust's compiler refuses to create one.
What two things does a &str store?A pointer to the first byte and a length.
