Threads, Arc and Mutex

Just enough concurrency to understand the data race in Lecture 2 and its fix.

In one sentenceThreads run code at the same time, and to share data between them safely you need Arc (shared ownership) plus Mutex (one at a time).
From the Rust Book: 16.1 Threads, 16.3 Shared state, 16.4 Send and Sync.

1. Starting a thread

use std::thread;

let handle = thread::spawn(|| {          // || { } is a closure: a mini function with no name
    println!("hi from the new thread");
});
println!("hi from main");
handle.join().unwrap();                  // wait here until the thread finishes

The two println!s can come out in either order. The OS decides who runs when. That unpredictability is the root of data races.

Without join(), main might finish first, and when main ends the whole program ends, killing the thread mid-way.

Remember from Part 1.3: every thread gets its own stack. Local variables in one thread are invisible to others. Sharing needs the heap or static memory.

2. move closures

let v = vec![1, 2, 3];
let handle = thread::spawn(move || {     // move: the closure takes ownership of v
    println!("{:?}", v);
});
handle.join().unwrap();

Without move, the closure would only borrow v. But the thread might outlive main's stack frame, so the borrow could dangle. Rust refuses to compile it. move hands v over to the thread completely.

3. Mutex: one at a time

use std::sync::Mutex;

let m = Mutex::new(5);
{
    let mut num = m.lock().unwrap();     // wait for the lock, then get access
    *num += 1;
}                                        // lock is released automatically here (Drop again!)
println!("{:?}", m);                     // Mutex { data: 6, .. }

A Mutex is a room with one key. To touch the data you take the key (lock()). Everyone else waits outside until you hand it back.

4. Arc: share ownership across threads

Several threads need to own the same Mutex. One owner isn't enough, so we need reference counting. Rc isn't thread safe, so we use Arc (Atomically Reference Counted). This is the Book's counter example:

use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];

for _ in 0..10 {
    let counter = Arc::clone(&counter);          // each thread gets its own Arc
    handles.push(thread::spawn(move || {
        let mut num = counter.lock().unwrap();
        *num += 1;
    }));
}
for h in handles { h.join().unwrap(); }
println!("{}", *counter.lock().unwrap());        // always 10

In Part 2.4 you'll write the unsafe version without a Mutex and watch it give wrong answers.

5. Atomics: a lock-free shortcut for numbers

use std::sync::atomic::{AtomicUsize, Ordering};
static HITS: AtomicUsize = AtomicUsize::new(0);
HITS.fetch_add(1, Ordering::Relaxed);    // read + add + write as ONE uninterruptible step

For a plain counter, an atomic is simpler and faster than a Mutex. (Ordering is an advanced topic: Relaxed is fine for counters.)

6. Send and Sync (just the idea)

  • Send: this type is safe to move to another thread. (Rc is not Send. Arc is.)
  • Sync: this type is safe to share by reference between threads. (Mutex is Sync.)

The compiler checks these automatically. Try to send an Rc to a thread and you get a compile error. This is how safe Rust makes data races impossible.

Check yourself

What does handle.join() do?Waits until that thread finishes.
Why do threads often need move?The thread might outlive the current function, so it must own its data instead of borrowing from a stack frame that could disappear.
Why Arc instead of Rc for threads?Arc updates its owner count with atomic operations, so it's safe when several threads clone and drop it at once. Rc isn't.
When is a Mutex lock released?When the guard returned by lock() goes out of scope and is dropped.
