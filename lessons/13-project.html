Project: memscope

One small tool that shows every idea from Lectures 1 and 2 happening inside a real running program. No libraries, just Rust.

In one sentencememscope prints your process's real memory map, logs every heap allocation, and runs each memory bug next to the safe version that stops it.

Run it

cd rust-memory-module/project
cargo run -- map
cargo run -- all        # everything, in lesson order
cargo test              # 12 tests that check each lesson's claims

How the heap logger works

Every Box, Vec and String asks one thing for memory: the global allocator. Rust lets you swap in your own. memscope puts a thin wrapper in front of the system allocator:

unsafe impl GlobalAlloc for Tracker {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 {
        let p = System.alloc(layout);        // the real allocator does the work
        record(Event::Alloc { addr: p as usize, size: layout.size() });
        p
    }
    // dealloc and realloc are wrapped the same way
}

#[global_allocator]
static ALLOC: Tracker = Tracker;

One catch: you can't println! inside alloc, because printing allocates, which calls alloc, which prints... forever. So events go into a fixed-size array (no heap needed) and get printed after recording stops.

Three things it found that the lessons don't mention

  1. UB changes with build mode. cargo run -- uaf reads 1234. cargo run --release -- uaf reads 1 and shows zero heap events: the optimiser deleted the allocations, because it's allowed to assume your code has no UB. Same code, different result. That's Part 2.1 in action.
  2. Only the main thread's stack is at the top. A test checking "heap is below stack" failed, because cargo test runs each test on a spawned thread, and spawned threads' stacks can be placed below the heap. The Part 1.2 map describes the main thread.
  3. Growing a Vec doesn't always move it. The allocator can sometimes extend a block in place (you can see String do this: 2 -> 8 bytes, grew in place). What's guaranteed is the opposite: a push that fits never moves it.

Make it yours: challenges

Do these yourself. Each one is small and uses only what you've learned.

  1. Easy: add a leak command that does Box::into_raw(Box::new(5)) and never frees it. Use trace to show an alloc with no matching free.
  2. Easy: in heap, add a Vec<u64> next to the Vec<u32>. Predict the allocation sizes before you run it.
  3. Medium: add a threads command that spawns 3 threads and prints the address of a local in each. Are the stacks near each other? Above or below the heap?
  4. Medium: add a test that Rc::clone causes no heap allocation (only the counter changes).
  5. Hard: add a double-free demo with Box::from_raw called twice. What does the tracker record? What does the system do?

Check yourself

Why can't the allocator print directly when it's called?Printing allocates memory, which calls the allocator again: infinite recursion. So it stores events in a fixed array and prints later.
Why does overflow write into a #[repr(C)] struct instead of two normal locals?repr(C) fixes the layout (buffer, then padding, then neighbour), so you see the same bytes every run. Normal locals can be placed anywhere the compiler likes.
Why did release mode show zero heap events for uaf?The code contains UB, and the optimiser may assume UB never happens. That let it remove the Box allocations entirely.
