From code to machine: rustc and LLVM

Who actually writes the machine code that lives in your program's text segment? Mostly a tool called LLVM.

In one sentencerustc checks your Rust code and translates it into LLVM's simple language, then LLVM optimises it and turns it into machine instructions for your CPU.
The name LLVM once stood for "Low Level Virtual Machine". Today it's just the name of the project.

A compiler in two halves

When you run cargo build, your code passes through two big programs:

  your .rs file
       │
       ▼
┌──────────────────────────────┐
│ rustc  (the "front end")     │  Rust-specific. Reads your code, checks types,
│                              │  checks ownership and borrowing (Lecture 3!),
│                              │  and refuses to continue if a rule is broken.
└──────────────────────────────┘
       │   LLVM IR: a simple, universal "middle language"
       ▼
┌──────────────────────────────┐
│ LLVM   (the "back end")      │  Shared by many languages: C, C++, Swift, Zig...
│                              │  Optimises the code, then writes real machine
│                              │  instructions for your exact CPU.
└──────────────────────────────┘
       │
       ▼
  machine code → goes into the TEXT segment of your program (Part 1.2)

Analogy: rustc is a strict editor who checks your essay follows every rule, then rewrites it in plain simple English. LLVM is a translator who takes that plain English and translates it into any language you need: Apple chip, Intel chip, or even Solana's virtual machine.

Why split it in two?

  1. Writing a good optimiser and machine-code generator for every CPU is huge work. LLVM has already done it, and is used by C++, Swift and others.
  2. So Rust's team only builds the Rust-specific part (rustc), and gets world-class speed on every CPU for free.
  3. That's why Rust can run on Macs, Linux servers, phones, tiny chips and blockchains.

See it for real: one function, three forms

Take foo from Part 1.3:

pub fn foo(input: i32) -> i32 {
    let y = input + 2;
    y * 3
}

1. LLVM IR in debug mode (what rustc hands to LLVM)

define i32 @foo(i32 %input) {
  %y = add i32 %input, 2      ; y = input + 2
  %_0 = mul i32 %y, 3         ; result = y * 3
  ret i32 %_0                 ; return it
}

It reads almost like your Rust, just one tiny step per line. i32 is still the same 4-byte type.

2. LLVM IR in release mode (after LLVM optimised it)

define noundef i32 @foo(i32 noundef %input) {
  %0 = mul i32 %input, 3      ; input * 3
  %_0 = add i32 %0, 6         ; + 6
  ret i32 %_0
}

LLVM did some algebra: (input + 2) × 3 = input × 3 + 6. Same answer, faster for the CPU. It also added noundef, a note to itself that says "I may assume this value is never garbage". Remember that: LLVM's assumptions are why undefined behaviour is so dangerous (below).

3. The machine code on my Mac (Apple M-series, ARM)

_foo:
    add  w8, w0, w0, lsl #1   ; w8 = input + input*2  (= input * 3)
    add  w0, w8, #6           ; w0 = w8 + 6
    ret                       ; return w0

Three CPU instructions. w0 and w8 are registers: tiny, super-fast storage slots inside the CPU itself. Notice: there's no stack frame here at all! The optimiser saw that y didn't need to live in memory and kept everything in registers. So the stack diagrams in Part 1.3 show the debug picture. In release, the compiler is allowed to skip memory whenever it can.

Why LLVM matters for Lecture 2

The optimiser is only allowed to rewrite your code because it assumes your program has no undefined behaviour. It never checks. It just trusts. So when UB does happen, the optimiser may have already rewritten the code in ways that only made sense if the bug wasn't there.

The memscope project caught exactly this. The use-after-free demo read 1234 in debug mode, but 1 in release mode, with zero heap allocations, because LLVM deleted the Boxes entirely. Same source code, different program. That's what "UB means anything can happen" looks like in real life.

Why it matters for Solana

Solana programs are written in Rust, but they don't run on an Apple or Intel chip. They run on Solana's own virtual machine, which uses a format called SBF (Solana Bytecode Format, based on eBPF). Because the back end is LLVM, Solana only had to teach LLVM to output SBF instead of ARM or x86. rustc stays the same. That's the sbpf-solana toolchain already installed on your Mac.

Try it (no install needed)

Save the foo function in a file foo.rs (add #[no_mangle] above it so the name stays readable), then:

rustc --crate-type=lib -O --emit=llvm-ir foo.rs   # creates foo.ll (LLVM IR)
rustc --crate-type=lib -O --emit=asm foo.rs       # creates foo.s  (machine code)
rustc -vV                                         # shows your LLVM version

Mine says LLVM version: 22.1.2.

Check yourself

Which part checks ownership and borrowing: rustc or LLVM?rustc. LLVM knows nothing about Rust's rules. By the time code reaches LLVM, it has already passed every safety check.
What is LLVM IR?A simple "middle language" between Rust and machine code. rustc writes it, LLVM reads it, optimises it and turns it into CPU instructions.
In release mode, foo had no stack frame. Why?The optimiser kept everything in CPU registers because nothing needed to live in memory. The compiler may skip memory whenever the result is the same.
Why can UB give different results in debug and release?The optimiser rewrites code assuming there's no UB. In release it optimises a lot, so a broken assumption has bigger, stranger effects.
How can Rust run on Solana's virtual machine?LLVM has a back end that outputs SBF bytecode. rustc's checks are the same, only the final translation changes.
