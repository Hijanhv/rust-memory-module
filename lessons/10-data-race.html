Data race

Two threads add 1 to the same counter at the same moment. One of the additions disappears.

In one sentenceA data race is two threads touching the same memory at once, at least one writing, with nothing coordinating them.

The four conditions

It's only a data race if all four are true. Remove any one and it's gone:

  1. Two or more threads run at the same time.
  2. They access the same memory.
  3. At least one access is a write.
  4. There's no synchronisation (no Mutex, no atomic).

Why COUNTER += 1 isn't one step

It looks like one action, but the CPU does three:

  1. Read COUNTER from memory into a register.
  2. Add 1 in the register.
  3. Write the result back to memory.

If another thread sneaks in between step 1 and step 3, an update is lost. Watch:

Real output from my Mac

$ cargo run --example 09_data_race
round 1: expected 8000, got 6151. 1849 updates lost.

8 threads × 1000 increments should be 8000. Nearly a quarter vanished on the very first try. Nothing crashed, nothing warned. Just a wrong number. Run it again and you'll get a different wrong number.

The lecture's exact code

The lecture's version starts 10 threads, each adding 1 once and then sleeping. I ran it 5 times on my Mac:

Final COUNTER (unreliable): 10     (5 runs out of 5)

No lost updates. Why? Each thread does just one increment, and threads start a little apart, so two of them rarely land inside the tiny read-add-write window at the same instant. The bug is still there, it's just rarely visible. That's why the lecture also offers a version that loops until an update is missed, and why the lab uses 8 threads × 1000 increments: more chances to collide, so you see it on the first try.

A bug that shows up 1 time in 10,000 is worse than one that shows up every time: it passes your tests and fails in production.

The safe fixes

Remove condition 4 by adding synchronisation:

use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::{Arc, Mutex};

// Fix 1: an atomic. Read-add-write happens as ONE indivisible step.
static ATOMIC: AtomicUsize = AtomicUsize::new(0);
ATOMIC.fetch_add(1, Ordering::Relaxed);

// Fix 2: a Mutex. Only one thread can hold the lock at a time.
let locked = Arc::new(Mutex::new(0));
*locked.lock().unwrap() += 1;
Try it 
cargo run --example 10_data_race_fixed

Prints atomic: 8000 and mutex : 8000. Every time. And notice: no unsafe anywhere.

Arc = "Atomically Reference Counted": lets several threads share ownership of one heap value. Mutex = "mutual exclusion": a lock.

UB doesn't stay inside the unsafe block

The unsafe block was one line, COUNTER += 1. But the wrong number shows up in the final println!, outside it. That's true for all three bugs: the overflow changed not_in_buffer, the use-after-free read y's data. Once UB happens, no part of the program can be trusted.

Optional, no install: the online Rust Playground has a button under Tools → Miri. Miri is a checker that runs your program slowly and watches every memory access. Paste any of the three bug examples in and it will name the bug instantly. You don't need it for this course.
